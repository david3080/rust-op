# 認証セキュリティの梯子 — rust-op の脅威モデルと形式検証の地図

このノートは、認証システムを「構造の複雑さ」で 0〜5 段に積み上げ、各段で
**どんな攻撃者が現れ、どんな機構がそれに答え、どんな前提の上に立つか**を整理したもの。
rust-op（FAPI2 級の OP）が、なぜ今ある機構を持つのかを段ごとに説明し、
本来の目標である**形式検証（前提の明示）**の地図として使う。

## このノートの読み方（最重要の原則）

1. **機構は「攻撃者」に答えるためだけに生まれる。** 攻撃者がいない段0では機構はゼロ。
   「なぜこの仕組みがあるの？」と思ったら、必ず **「それはどの攻撃者に答えているのか？」** を問う。
2. **「安全」は1つのチェックリストではない。** システムの全ての箱・全ての境界に対する
   攻撃の**総和**。1つの機構は自分の箱の攻撃者にしか答えない（銀の弾丸は無い）。
3. **少数の“原子”が、構造が育つたびに大きな形で再登場する。** セキュリティは千個の
   バラバラなルールではなく、少数の原子の組み替え。
4. **完全に正直な主張の形**: 「**約束Z は、攻撃者X に対し、前提Y の下で成り立つ**」。
   「安全」はこの三つ組（Z・X・Y）の集まりでしかない。これを書き下すのが形式検証。

## 再登場する“原子”

| 原子 | 意味 | 初登場 |
|---|---|---|
| 秘密 | 本人だけが知る/持つもの | 段1 |
| 推測不能 | 当てずっぽうで作れない | 段1 |
| 指紋保存(hash-at-rest) | 保管庫が漏れても使えるものが出ない | 段1 |
| 単回/新しさ | 一度きり・録音再送が効かない | 段2(誕生) → 段4(認可コード) → 段5(マンデート) |
| 束縛(binding) | 正しいオリジン/相手/鍵/操作にだけ効く | 段3(オリジン) → 段4(PKCE,DPoP,aud) → 段5(binding message) |
| 範囲(scope) | 許したぶんだけ | 段4 |
| 通信路機密性 | 回線で漏れない | 段2 |
| 認証 | 同じ人か | 段1〜（全段で再利用） |
| 同意(consent) | 利用者が明示的に許す | 段4 |

## 段0: まだ何も守らなくていい世界（出発点）

- **構造**: 一人・1台・共有なし・ネットなし。
- **攻撃者**: いない。
- **守りたい約束 / 機構 / 前提**: 無い（守る相手がいない）。端末が物理的に自分だけのもの。
- **キモ**: セキュリティ機構ゼロの地点。ここから構造を一段足すたびに攻撃者が1人増え、機構が1つ生まれる。

## 段1: 1台を複数人で（共有の物理デバイス、ネットなし）

ユースケース: 家庭/学校の共用PC、銀行ATMの端末部分。

- **構造**: 1台を複数人で使う。誰が誰かを区別するため各自が秘密（パスワード等）を持つ。
- **新しい攻撃者**: 同じ端末の他の利用者、肩越しに覗く人、物理アクセスできる人。
- **守りたい約束**: 本人だけが本人として使える。他人になりすませない。
- **機構 + 前提**:
  - 推測されにくい秘密（前提: 推測不能）
  - 指紋(ハッシュ)で保存（前提: 保管庫を読まれても元秘密は出ない）
  - 照合も漏らさない（定数時間比較）
  - 試行回数制限（ロックアウト）
- **段1の「必要なこと」は5点セット**: 認証 ＋ セッション寿命(自動ロック/ログアウト) ＋
  隔離(OSの利用者別権限＝認可) ＋ デバイス信頼(TCB) ＋ 物理(ディスク暗号化/耐タンパ)。
  → 認証だけでは段1の中ですら不十分。
- **キモ**: ネットが無くても「秘密・推測不能・指紋保存・試行制限」が要る。これが認証の原子。
  「単回」はまだ不要（録音再送する回線がまだ無い）。

### 注: ATM は段1と段2のはざま
ATM の**端末**は段1（共有の物理デバイス: スキマー、温まったセッション、物理改ざん）だが、
**認証アーキテクチャ**は段2（採取データが回線を流れ、中央テンプレートと突合）。
OKB の手のひら静脈をサーバ保存して毎回突合するのは段2の現象。**現実のシステムは段をまたぐ**。

## 段2: ネイティブアプリ + 専用サーバ（回線が増える）

- **構造**: 端末（アプリ）と遠くのサーバが回線でつながる。秘密やデータが端末を離れて回線を通る。
- **新しい攻撃者**: 回線の上にいる者（中間者）— 盗聴・改ざん・記録して再送(リプレイ)・サーバなりすまし。
  加えて、データが集まる**遠くのサーバ自体**（内部犯・侵害・中央DBという一点の標的）。
- **守りたい約束**: 秘密が回線で漏れない/相手が本物のサーバ/書き換えられない/古いやり取りが通らない/中央保管が漏れても致命傷にならない。
- **機構 + 前提**:
  - TLS（暗号化＋サーバ認証）。**前提: 証明書を保証するCAを信じる**（信頼は推移し最弱リンクの強さしか出ない、の初登場）。
  - **単回/新しさの初登場**: サーバが毎回使い捨ての乱数(チャレンジ/nonce)を出し、録音した古い応答を弾く。
  - セッショントークン（毎回パスワードを送らない）。「盗まれたら?」が段3/4の送り主束縛への伏線。
  - 中央保管はハッシュ/暗号化、鍵はHSM、生体ならキャンセラブル生体。**前提: 他人が運用する遠くのサーバを信じる**。
- **キモ**: 「回線」という1人を足しただけで、暗号化通信路・サーバ認証(CA)・**単回の初登場**が呼ばれる。

## 段3: ブラウザでネット越し（Webアプリ）

- **構造**: 利用者は**ブラウザ**という共用の実行環境を通す。ブラウザは「多数サイトのコードを同時に動かす」「Cookieを自動で付ける」「スクリプトを実行する」「リダイレクトで渡り歩く」「フロントは利用者のマシン上＝改変可能」。
- **新しい攻撃者**: 別タブ/別サイトの悪意あるページ（CSRF）、注入スクリプト（XSS）、リダイレクト横取り（オープンリダイレクト）、フロントエンドそのもの（信用できない）。
- **守りたい約束**: 別サイトが勝手に操作できない/セッションを盗まれない/戻り先が登録値だけ/フロントに秘密を置かない。
- **機構 + 前提**:
  - Cookie衛生: `HttpOnly`/`Secure`/`SameSite`（rust-op の `finalize_login`）＋ stateパラメータ。
  - XSS対策: 出力エスケープ＋CSP＋秘密をJSから触れない所に。
  - **redirect_uri 完全一致**（rust-op の `CheckRedirectUri`）。
  - フロント不信: 認可はサーバ側で完結。**前提: ブラウザの同一オリジンポリシー(SOP)を信じる**。
- **キモ**: ブラウザの“親切”がそのまま攻撃面。「リダイレクトでパラメータを運ぶ」性質が段4のコード横取りの土壌になる。

## 段4: 第三者アプリにAPIアクセスを許す（OAuthの誕生）— rust-opの本拠地

たとえ: 車のバレットキー（限定された一時的な許可を渡す。マスターキー＝パスワードは渡さない）。

- **構造**: あなたでもあなたのサーバでもない**第三者（クライアント）**が、あなたの代理でサーバにアクセス。
  委譲の三角形: リソース所有者(あなた)／クライアント／認可サーバ＋リソースサーバ。
- **新しい攻撃者**: 部分信頼の第三者（悪意/ずさん/過剰要求）、クライアントなりすまし、トークン窃取（bearer）、認可コード横取り、同意フィッシング/過剰scope、取り違え(confused deputy)。
- **守りたい約束**: 同意した範囲だけ・期限つき・取り消せる/パスワードを見せない/盗まれたトークンは他人に無効/横取りされたコードは交換不能/正しい相手・正しいリソース。
- **機構 + 前提（攻撃者ごとに召喚）**:
  - パスワードでなく**トークン**（範囲/期限/失効）。
  - **認可コードフロー**: 認可サーバで認証(passkey)＋同意 → 使い捨ての**認可コード**（=段0の単回が主役化）→ サーバ間でトークンと交換。
  - **PKCE**（コード横取り対策。rust-op `CheckPkce`）。
  - **送り主束縛(DPoP/mTLS)**（トークン窃取対策）。
  - **クライアント認証(private_key_jwt/secret)＋redirect完全一致**（なりすまし対策）。
  - **aud/リソース束縛＋発行者識別**（取り違え対策）。
  - **PAR＋JAR**（ブラウザURL上のパラメータ改変対策）。
  - **OIDC**: ID token（署名付き身元主張＋aud束縛＋nonce）。
  - **前提**: 認可サーバが同意/scopeを正しく強制する。クライアントとサーバが事前に登録し合っている（→ **DCR**）。
- **キモ**: 初めて「あなたでもサーバでもない相手」に権限を渡す。OAuth/FAPIのほぼ全部はこの委譲を
  範囲つき・期限つき・取り消せる・盗難/横取り耐性・正しい相手/リソースにする機械。
  下の段の認証は消えず再利用される。**FAPI2＝段4の強化版**（PAR/PKCE/送り主束縛を必須化、弱い選択肢を禁止）。

## 段5: 承認が切り離される委譲（CIBA）

たとえ: 「誰かがあなたの名義でログイン/決済しようとしています。承認しますか？」を手元のスマホで承認。

- **構造**: 要求を出す人（消費デバイス: コールセンター/決済機/バックエンド）と、承認する人（あなた、認証デバイス=スマホ）が**別デバイスに分かれ、ブラウザのリダイレクトで繋がっていない**。クライアントはバックチャネルで要求→`auth_req_id`→ポーリング。
- **新しい攻撃者**: 「何を承認しているか見えない」を突く社会工学（攻撃者の操作を承認させる）、プッシュ爆撃/疲労（無認証でスマホに依頼を飛ばす）、結果横取り（auth_req_id）、時間差、敵対的な消費デバイス。
- **守りたい約束**: 意図したものだけ承認/あなただけが承認/起こしていない要求で洪水・誘導されない/権限は単回・範囲・期限/結果は正規クライアントだけへ。
- **機構 + 前提**:
  - **binding message**（人間可読の説明をスマホに表示）＋ **authorization_details/マンデート(RAR)**（rust-op の `authorization_details`/`mandate_consumed`）。
  - 認証デバイスでの強い認証（passkey承認＝段1〜3の再利用）。
  - **レート制限**（rust-op `ciba_rate`、(client,account)毎）＋ 起案は登録クライアント認証必須。
  - トークンのポーリングもクライアント認証＋**auth_req_id は推測不能・単回**。
  - マンデートは単回＋範囲＋期限（`mandate_consumed` を CAS、`/oauth/mandate/consume`）。
  - **前提: binding message が忠実に表示され、かつ利用者が実際に読む**（人間という最弱リンク）。
- **キモ**: 「誰が要求するか」と「誰が承認するか」が分離。要求と承認の見た目の結びつきが切れるので、
  承認を**その具体的操作に再束縛**（binding message＋マンデート）し、**時間と回数で縛る**（単回・期限）。
  段4の委譲から**ブラウザを抜き、切り離し承認を足した**もの。

## 横断する2本の軸（全段に効くレンズ）

### 軸A: 利用者は味方か、敵か（委譲可能性）
- **味方**（情報を守りたい）: 利用者と守る側の利害が一致。本人は秘密を守る。
- **敵**（出席代返・試験・KYC・サブスク共有・DRM）: 利害が対立。本人は資格情報を進んで渡す。
- 三要素を**委譲可能性**で並べ直すと: 知識=渡せる、所有=渡せる、**生体=渡しにくい（非委譲）**。
  → 「本人が自分を代理させるのを防ぐ」要件では非委譲な生体だけが効く。
- ただし生体でも閉じきれない（偽物提示、最初だけ顔出して去る）。出席は「身元」でなく
  「**一定時間ずっと居て、やっていたこと**」＝瞬間の身元より難しい → 非委譲生体＋liveness＋連続チェック＋
  **制度的backstop（検出＋罰則）**。利用者が敵になりうる問題は純技術では終わらない。

### 軸B: 資格情報を持ち歩くか、身体だけ来るか
- 分かれ目は「自分の資格情報を持ち歩くか／身体だけ来るか」:
  - **passkey**: 端末(鍵)を持ち歩く → サーバは公開鍵だけ、生体はローカル、中央保管なし。
  - **カード式静脈(match-on-card)**: カードを持ち歩く → テンプレートはカードの中。
  - **カードレス静脈(OKB)**: 身体だけ → 中央にテンプレート保存＋遠隔照合が**強いられる**。
- この軸は「**何が回線を流れ、何が中央に貯まるか**」、さらに「**そもそも開放標準にできるか**」まで決める。
  passkey/FIDO が綺麗に標準化できたのは公開鍵だけ交換するから。身体だけ・中央はベンダー密結合＋
  生体集約が規制対象で標準化しにくく、**FIDO級の開放標準は無い**（IEEE 2410/BOPS はニッチで、
  しかも永続的サーバ保存を避ける方向に進化）。中央生体が標準的に動くのはほぼ国家ID（Aadhaar 等）。

## 認証(AAL) vs 身元保証(IAL) — 直交する2層

- **認証(Authentication)**: 「前に登録した“その人”と同じか」。毎回。現実の誰かは言わない。
- **身元確認(Identity Proofing/Assurance)**: 「現実世界の誰で、どれだけ確かか」。登録時に一度。
- **NIST SP 800-63** が3本に分離: **AAL**(認証強度)/**IAL**(身元確度)/**FAL**(連合主張強度)。
  **IALとAALは直交**（高AAL＋低IALも、低AAL＋高IALもありうる）→ 別々に宣言せよ。
- **passkeyは「同じ人」を完璧に証明するが「誰なのか」は一切証明しない。** 両者は独立。

### 身元のライフサイクル（箱ごと）
1. 身元確認(登録)＝IAL ← rust-op は薄い  2. 資格情報の紐付け(登録時乗っ取り注意)
3. 認証(毎回)＝AAL ← rust-op は強い  4. 認可  5. フェデレーション＝FAL  6. 復旧/失効(最弱になりがち)

### rust-op の現在地と将来拡張
- 今: **AAL 強い**（passkey, DPoP, `acr`/`auth_time`, ステップアップ認証）／**IAL ほぼ1**（メール到達確認＋自己申告claim）。
- **拡張A（最優先・コードほぼ不要）**: 各claimの保証レベルを明示（email=制御確認 / name=IAL1）。
  これが「前提の明示」そのもの＝形式検証の実作業。
- 拡張B: OIDC4IDA の `verified_claims` で「検証済み」を構造化して運ぶ。
- 拡張C: 高IAL資格情報を取り込む（マイナンバー/JPKI or VC）。**passkey=日常認証、マイナ=一度きりの身元確認**。
  デジタル庁「デジタル認証アプリ」が OIDC 認可コードフローを提供するので、rust-op は RP として接続するだけ（コードは素直）。
  **実質の壁はコードでなく、利用資格・審査／規制責任／そもそも今必要か**。
- 拡張D: ステップアップ“身元”保証（既存のステップアップ認証の対称形）。
- 拡張E: 身元確認済みIdPとして他者に FAL 付きで主張。

## フェデレーション と DID/VC（2つの信頼の形）

- **OIDC/SAML フェデレーション（IdP中心・星形）**: 毎回IdPに問い合わせ、IdPがその場で身元を主張。
  IdPが行き先を全部知る。rust-op は**もうこのプロトコルを話している**（ID token/discovery/JWKS）。
  本当のフェデレーションの一歩は (a) 他組織RPがrust-opを信じる、(b) rust-opがGoogle等を信じる。
- **DID/VC（持ち主中心・三角形 Issuer→Holder→Verifier）**: 署名つき証明書を財布に持ち、提示するだけ。
  発行者は問い合わされず行き先を知らない。選択的開示が可能。識別子(DID)は中央が発行しない。
  - 正直な注意: **“分散”は trust anchor を消さず場所を移すだけ**（検証者はどの発行者を信じるかのリストが要る）。
    自己主権の裏返し＝鍵管理・復旧が自己責任（鍵紛失＝身元喪失）。成熟度はOIDCより手前だが EUDI/mDL が実装を強制中。
  - OAuth/OIDC知識はほぼ転用可（橋＝**OID4VC/OID4VP**、EUDIウォレットも採用）。

## rust-op の位置と、このセッションでやったこと

- rust-op は **段4〜5 に住み、段1〜3 の全部の上に建つ**。FAPI2＝段4の強化版。
- このセッションの作業を段でマッピング:
  - **制御つきDCR（PR #12/#16/#17/#18）**: 段4のクライアント登録の信頼境界。IAT単回(段0の単回)、
    resolve_client、/oauth/register、レート制限、revoke-client。本番 e2e 検証済み。
  - **非中核掃除（PR #19）**: 段4の弱い選択肢を削る（client_secret_post 等）＝optionality削減＝証明面積の縮小。
    fido/(実passkey検証コア)は除外。
  - **CIBA 実 e2e**: 段5 を端から端まで検証（backchannel→アプリpasskey承認→token+id_token発行）。

## 形式検証への接続（本来の目標）

この梯子そのものが**形式検証の地図**。各段＝各「箱」に固有の攻撃者・機構・前提がある。
「前提を明示する（拡張A）」とは、各箱について
**「約束Z は 攻撃者X に対し 前提Y の下で成り立つ」** を1つずつ書き下すこと。

- 種は既にある: 段0で書いた「**引換券は一度きり（単回消費）**」の仕様。
  - 約束Z = 1枚の引換券で受け取り成功は高々1回。
  - 前提Y = (A原子的消費)＋(D単一保管庫)が核。Bで意味を持つ。Cは別約束(漏洩耐性)。
  - これを段1で property test(Haskell/QuickCheck)→段2で Alloy →段3で Lean、と上げていける。
- 次の一歩: rust-op の各約束（単回・redirect完全一致・PKCE束縛・送り主束縛・マンデート単回…）を、
  この三つ組の形で1枚に書き下す。

## 検証アーキテクチャ（道具の3系統と「層になった前提のスタック」）

### 道具の3系統（それぞれ違う問いに答える）
| 系統 | 問い | 攻撃者 | 代表 |
|---|---|---|---|
| A 記号的プロトコル検証 | プロトコルの論理は健全か | 組み込み(Dolev-Yao) | **Tamarin**, ProVerif, Verifpal |
| B 計算量的(暗号)証明 | 暗号構成が確率・計算量的に安全か | 確率的 | CryptoVerif, EasyCrypt |
| C 汎用モデリング/証明 | 任意の不変条件・状態 | 自作 | Alloy, TLA+, Lean/Coq, （実コード: **Kani**/Creusot/hax） |

主要ツール早見: Alloy(★/有界/反例図)・Verifpal(★★/入門)・TLA+(★★/並行不変条件)・ProVerif(★★/無界自動)・
Tamarin(★★★/無界・状態・本気のプロトコル証明)・Lean/Coq(★★★/汎用手証明)・EasyCrypt(★★★★/暗号)・Kani(★★/実Rust有界)。

区別する4軸: **記号的 vs 計算量的** / **有界 vs 無界** / **攻撃者が組み込み vs 自作** / **モデル vs 実コード**。

### 層になった前提のスタック（rust-op の総セキュリティ主張の構造）
総主張 = 全層の連言。各層に道具と「明示された前提」があり、**層間は人手で橋渡し**する。

| 層 | 道具 | 産むもの／前提 |
|---|---|---|
| プロトコル論理 | **Tamarin** | 防げる攻撃＋抽象前提(チャネル機密・単回・新鮮nonce・束縛…)を導出。**理想暗号を仮定** |
| コード＝モデル | **Kani(局所)＋手の対応づけ＋テスト**(将来 hax/DY*) | ギャップは**明示された人手discharge前提**として残る(自動ブリッジ無し) |
| プリミティブ | (外部)HACL*/監査 | 一部のみ機械証明済み。ECDSA等は信頼＋監査 |
| 実装 | 監査＋RUSTSEC監視＋`subtle`等 | サイドチャネル・実装バグは**監視する前提** |
| RNG・鍵 | CSPRNG・Cloud KMS | rust-op が一部充足 |

### Tamarin↔Kani の橋（健全な自動ブリッジは無い）
- 二つは別世界: Tamarin＝抽象モデル(メッセージ・役割・記号的暗号)、Kani＝具体Rust関数(バイト・有界入力)。
- 橋は**人手の対応づけ**: **Tamarinの仮定 ＝ Kaniの証明義務**（例: Tamarinは「コードは単回」と仮定、
  Kaniは「consumeが単回(保管庫が原子的なら)」を証明して仮定を discharge）。モデルの各遷移ガードを
  実装Rust関数に対応づけ、「局所検査の合成が遷移を実装」と人が論じる＋テストで補強。
- **モデル–実装ギャップ＝「形式検証したのにハッキングされた」物語の住処**。
- Rust固有の前線: **hax(Rust→ProVerif/F*)** / **DY*(F*でコード＝モデル)**。研究グレード・F*中心・専門的。

### 暗号は前提（ただし明示する）
- 記号的検証は**理想暗号を仮定**(署名は鍵なしに偽造不能 等)＝正しい境界の引き方。暗号自体は証明しない。
- **「全部 CryptoVerif/EasyCrypt 証明済み」ではない**: HACL*/Project Everest は一部の実装を F* で検証。
  一方 ECDSA(ES256) は標準モデルできれいに証明されず、RustCrypto の p256/rsa 等は監査されるが機械証明ではない。
  教訓: rsa クレートに timing サイドチャネル(Marvin系)が報告された——アルゴリズムが健全でも実装にバグは出る。
  「ライブラリに脆弱性なし」は**過去に破れた、明示して監視する前提**(RUSTSEC追跡)。
- 実装レベルの暗号前提: 定数時間比較(rust-op は `subtle` で対応済)・nonce/RNG・鍵管理(rust-op は Cloud KMS)。

### Tamarin で「網羅」できるか（スコープの正直な答え）
- Tamarin が網羅的に出すのは **(述べた性質について)(モデル化したフローの)プロトコル層の前提**。
- ただし2つの限界:
  1. **層の限界**: 暗号実装・コードギャップ・運用/人間(Firestore原子性・KMS・レート制限・binding message を人が読む)は
     Tamarin の外。これらは他の層の道具・明示で埋める。Tamarin＝最重要だが**1層**。
  2. **性質完全性の限界**: Tamarin は**述べた性質**の前提しか出さない。「全部の性質を述べたか」は人の判断。
     → その判断の道具が**この梯子(脅威モデル)**。各段/各箱が「述べるべき性質」のチェックリストになる。
- ゆえに **網羅 = 梯子(性質の網羅) × Tamarin(性質ごとの前提導出) × 他層**。Tamarin は必須の一因子であって全部ではない。

### Tamarin モデリング・ロードマップ（rust-op、増分で網羅へ）
各モデルが「防げる攻撃＋必要前提」を産む。順に積む:
1. **認可コード + PKCE + PAR → トークン**（委譲の核）: 性質=正規クライアント/認証済ユーザにのみ発行、コード単回、
   PKCE束縛、redirect完全一致。surfaced前提: コード推測不能+単回, verifier秘匿+束縛, クライアント認証, TLSチャネル。
2. **DPoP 送り主束縛**: 性質=トークンが DPoP 鍵に束縛、盗難 bearer 無効、proof 新鮮(htu/htm/jti単回)。
   前提: DPoP鍵秘匿+毎回生成, jti単回, RS が cnf.jkt 検査。
3. **CIBA + RAR マンデート**: 性質=正規ユーザが「その具体的要求」を承認後にのみ発行、マンデート単回・拡張不可、
   結果は起案クライアントのみ。前提: binding message 忠実表示+**利用者が読む**, auth_req_id 推測不能+単回, クライアント認証(起案+poll)。
4. **WebAuthn ユーザ認証**: 性質=正規ユーザのみ有効アサーション、オリジン束縛(anti-phishing)、challenge新鮮、signcount(anti-clone)。
   前提: challenge 推測不能+単回, rpId/origin 束縛忠実, 認証器鍵秘匿。
5. **OIDC ID token**: 性質=偽造不能, aud束縛, nonce新鮮。前提: 署名鍵秘匿(KMS), nonce単回。
6. **合成**: CIBA発行×DPoP束縛×RARマンデートのトークンをRSで使う、等の跨ぎ性質(合成は別物・最難)。

注: Tamarin は**1モデル＝1フロー/性質**。「全部を一つの巨大モデル」は非現実的で、上記を**性質ごとに積む**ことで
網羅へ近づく。各モデルは数十〜百行の `.spthy`、本気の合成証明は専門家の数ヶ月〜年(FAPI のWG解析も auth code と CIBA のみ)。
実行は macOS なら `brew install tamarin-prover`。モデルを書く ↔ 走らせて反例/証明を見る、を反復する。
